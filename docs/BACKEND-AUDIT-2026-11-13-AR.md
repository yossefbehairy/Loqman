# مراجعة جاهزية الباك إند — 13 نوفمبر 2026

تحديث بعد التنفيذ في اليوم نفسه. هذه الوثيقة تحفظ نتائج المراجعة الأصلية. إصلاحات قاعدة البيانات ونقل الأحداث وحدود المحركات، وإضافة MCP والموافقات والمتصفح، ونتائج الاختبارات الحية موثقة في [خطة التنفيذ المحدثة](AGENT-BACKEND-ROADMAP-AR.md) و[دليل العامل](PYWORKER.md).

النطاق: Python worker وSQLite والمحركات ومسارات الأدوات وIPC والتغليف، مع فحص المواضع التي تؤثر فيها طبقة Electron على وصول أحداث الباك إند. المراجعة قراءة للكود وتشغيل اختبارات على بيانات مؤقتة؛ لم تُنفذ طلبات نماذج حقيقية أو تحكم في جهاز المستخدم. التغييرات المحلية غير الملتزمة موجودة أصلًا وتشمل MCP تجريبيًا وسياسة أدوات؛ لم تُعامل ككود صدر بالفعل.

## الحكم

أساس الـworker موجود ويستخدم standard library، لكن المنتج غير جاهز بعد للإعلان عن MCP متكامل أو كتابة آمنة أو تحكم بالجهاز، وتوجد عيوب موثقة في سلامة البيانات والأحداث يجب إصلاحها قبل إصدار يعتمد عليه مستخدمون. النجاح في mock لا يعني اختبار المحركات الحقيقية.

## عيوب مؤكدة وعالية الأولوية

1. **قبول قاعدة بيانات أجنبية وتعديلها (P1).** `backend/pyworker/db/migrate.py:102` يعتبر وجود اسم جدول واحد معروف دليلًا كافيًا على ملكية قاعدة البيانات، ثم ينشئ الجداول ويرفع schema version. تجربة على قاعدة مؤقتة فيها جدول `missions` أجنبي فقط: `init_db` قبلها، أضاف 19 جدولًا وصنع نسخة احتياطية. الاختبار الحالي `backend/tests/pw/test_schema_compat.py:33` يكرس نفس الحالة كترقية صالحة. عند فتح ملف خاطئ قد يلوثه ويعتبره صالحًا. المطلوب: تعريف هوية schema للتحقق قبل WAL أو DDL، وخطة توافق مع النسخ القديمة الحقيقية ورفض الغامض، مع اختبارات قواعد أجنبية فيها أسماء مشتركة، ونسخة احتياطية قبل أي تغيير قابل للرجوع. اختبار حالة الإصدار الحالي ناقص الجداول أيضًا ضروري.

2. **سباق يضيّع أول أحداث stream في Electron (P1).** `frontend/electron/worker-client.cjs:55` يعالج عدة رسائل من دفعة stdout في callback واحد؛ استجابة `stream.open` تحل Promise ثم يمكن أن يعالج callback حدث stream قبل تشغيل تكملة Promise. `frontend/electron/main.cjs:83` يسقط الحدث إذا لم يُسجل المالك بعد، والتسجيل لا يحدث إلا في `:159`. buffer الموجود في preload لا يعالج ما تم إسقاطه في main. أعدنا إنتاج الترتيب باستدعاء WorkerClient لاستجابة ثم stream في نفس دورة التنفيذ: المالك سُجل لاحقًا وعدد الأحداث الموصلة صفر. النتيجة المحتملة: اختفاء replay أو completion مبكر، خاصة run انتهى بالفعل. يلزم handshake أو buffering محدود حتى تسجيل المالك واختبارات فعلية تغطي response+events في chunk واحد وstream_end المبكر وdisconnect.

3. **streams المهام والتنفيذ المنتهي لا تُغلق تلقائيًا (P1/P2).** `backend/pyworker/streams.py:95` يرسل snapshot للمهمة ثم ينتظر دائمًا أحداثًا جديدة، حتى لو انتهت، ولا ينهي بعد حدث نهاية حي. `_pump_execution` في `:117` يعيد التاريخ ثم ينتظر حتى لو التنفيذ منتهٍ. حد streams هو 64؛ مع مستهلكين لا يغلقونها يمكن استنفاده ورفض اشتراكات جديدة. الاختبار `backend/tests/test_pyworker_streams.py:48` يقر أن التنفيذ المكتمل ينتظر حدثًا جديدًا ويغلقه يدويًا. المطلوب إغلاق deterministic بعد terminal snapshot/live event واختبار عدم التسرب والسباق مع الاشتراك.

4. **مخرجات CLI غير محدودة وقت التجميع (P2).** Claude وCodex وOpenCode والـagy القديم يستعملون `proc.communicate()` ثم يقتطعون النص بعد جمع stdout/stderr في الذاكرة؛ انظر `backend/pyworker/runtime/claude_runtime.py:276` و`codex_runtime.py:341` و`opencode_runtime.py:190`. الحد `MAX_OUTPUT_CHARS` لا يمنع عملية تابعة من استهلاك ذاكرة كبيرة قبل اكتمالها. يلزم قراءة bounded بالتزامن للقناتين مع إنهاء process tree عند تجاوز الحد، واختبارات fake CLI لمخرجات ضخمة وtimeout/cancel. ACP لديه حدود منفصلة، فلا يُعمم عليه هذا الحكم.

5. **استرجاع أحداث mission/execution غير متكافئ مع run (P2).** `streams.py:95` و`:117` لا يستخدمان `last` رغم أن `stream.open` يقبله لكل topic. المهمة تعيد الحالة الحالية فقط لا سجل تغييراتها؛ التنفيذ يعيد التاريخ كاملًا بدون cursor ويحصل تكرار عند reconnect. المطلوب تحديد contract صريح لكل stream، أو تخزين وترقيم الأحداث القابلة للاسترجاع مع dedupe، واختبار فصل الاتصال أثناء البث وبعد النهاية.

## وظائف ناقصة قبل تسليم الأدوات

6. **MCP لا يصل إلى المحركات.** `backend/pyworker/mcp_workspace.py:1` سيرفر قراءة تجريبي مستقل، و`core/run_tools.py:1` وسيط داخل العملية؛ لا يوجد ربط production بينهما وبين engine أو run. `api/system.py:65` يصرح بعدم دعم tool approvals وworkspace restriction. مطلوب قناة MCP آمنة محدودة بالـrun، policy عند list وcall، عمر عملية وcleanup، واختبار CLI حقيقي إلى جانب fake client. لا يُعتمد `--allow-read` كعزل لنظام الملفات.

7. **الموافقات والكتابة والأدوار.** `core/approvals.py:3` يخزن الموافقات لكنه لا يوقف أي adapter ولا يوقظه، و`core/deliverables.py:1` ينشئ مسودة قابلة للتنزيل ولا يكتب داخل workspace. لا يوجد ربط profile بالمحادثة الجديدة في `api/convo.py:63`. يلزم ربط طلب الأداة بمعرف run ومدخلاته وقرار المستخدم ومهلة واضحة، ثم كتابة آمنة بخطوة مستقلة واختبارات رفض/إلغاء/restart والتكرار. حماية الموافقة من أفعال computer-control تحتاج تصميمًا واختبارًا قبل إضافته.

8. **المتصفح والتحكم بالجهاز غير منفذين.** يتطلبان browser service وعزل جلسة وسياسة شبكة ورفع/تنزيل وتقييد ملفات وتنافس على التحكم، ثم Windows CUA driver وإدارة عمره. لا يعني وجود أدوات CEO أو `workspace_read` أن أيًا من هذين متاح.

9. **بث النص واستكمال جلسات المحرك غير متوفرين كقدرات موحدة.** `runtime/claude_runtime.py:22` و`runtime/codex_runtime.py:35` يذكران stateless وعدم streaming؛ أحداث run حاليًا حالة التشغيل فقط. انتهاء الإلغاء البعيد غير مؤكد عبر المحركات. مطلوب اختبار capability لكل adapter وعدم تعميمها.

## تحقق وتسليم

- نتيجة التشغيل الحالي: `backend\.venv\Scripts\python.exe -m pytest backend/tests -q -ra` → **279 passed, 1 skipped** في 43 ثانية؛ المتخطي اختبار symlink على Windows. هذه تشمل اختبارات MCP وpolicy المحلية غير الملتزمة، ولا تثبت التوافق مع MCP SDK أو محرك حقيقي.
- اختبار قاعدة البيانات الأجنبية تم على ملف SQLite مؤقت مستقل. اختبار ترتيب رسائل Electron كان محاكاة حتمية لمعالجة رسالتين في callback واحد، وليس تشغيل Electron كاملًا.
- CI في `.github/workflows/ci.yml` يشغل backend وE2E على Ubuntu؛ المنتج المستهدف Windows، ولا توجد فيه بوابة Windows لتغليف worker أو smoke مثبت نظيف. أضف Windows job مع Python 3.13، اختبارات junction/paths، بناء frozen exe وتشغيل smoke في بيانات مؤقتة.
- لا توجد في هذا التدقيق تجربة استعادة على نسخة مستخدم حقيقية آمنة، ولا تثبيت clean Windows profile، ولا اختبار حي للمحركات الأربعة أو حدود الحساب والفوترة. backup/restore لديه اختبارات معزولة لكنها ليست دليلًا على جميع هذه السيناريوهات.
- `backend/pyworker/db/core.py:64` يستخدم SQLite connection واحدة و`busy_timeout=5000` على event loop، و`core/conversation_runs.py:370` يحمل الملفات بشكل متزامن؛ ضغط القرص أو lock قد يؤخر requests/cancel. هذا خطر تصميم يحتاج benchmark واختبار lock فعلي قبل تحديد شدته، وليس عطلًا أُعيد إنتاجه هنا.
- إعدادات adapters مختلفة من حيث الأدوات وhooks والبيئة؛ قياس الفوترة/الحصة وصحة cancel البعيد يتطلب تجارب منفصلة بموافقة المستخدم، ولا يُستنتج من اختبارات fake.

## ترتيب الإصلاح

1. حماية قاعدة البيانات والتحقق من schema قبل أي mutation، ثم اختبار ترقيات وrestore على نسخ معزولة.
2. إصلاح فتح/إنهاء/replay streams في worker وElectron واختبارات السباق.
3. حدود مخرجات subprocess وعدم حجب event loop وإغلاق العمليات عند الإلغاء.
4. شريحة أداة واحدة: run → سياسة → MCP → قراءة، ثم موافقة مرتبطة بالمحتوى وكتابة آمنة؛ اختبار حقيقي لمحرك واحد.
5. باقي المحركات، البث والجلسات، ثم browser وCUA طبقًا لقدرات مثبتة.
6. Windows CI وfrozen build وclean-install وrestore، ثم توثيق قدرات كل محرك وحدوده.
