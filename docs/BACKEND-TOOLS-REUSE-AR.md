# إعادة استخدام RuseBot: أدوات الباك إند والمراحل

تاريخ المراجعة: 11 نوفمبر 2026. المصدر: نسخة `D:/OpenMausBot` المحلية، ويعرض `package.json` فيها الإصدار `0.1.124`. تمت قراءة السورس والاختبارات؛ لم يتم تشغيل RuseBot أو المتصفح أو CUA، ولم يُنقل كود تنفيذي. المراجعة تخص الباك إند، مع ذكر تشغيل driver داخل Electron عند الحاجة؛ لا تتضمن تطوير واجهة React.

## القرار

نأخذ تصميم طبقة الأدوات وربطها بالمحركات، ونكيفه مع FastAPI وSQLite وRun Manager الموجودين. نبدأ بسياسة أدوات فعلية وMCP محدود، ثم المتصفح، ثم التحكم بجهاز Windows. لا ننسخ السيرفر أو طبقة التخزين بالكامل.

وجود browser أو computer MCP لا يكفي: adapters الحالية عندنا لا تمرر هذه التكاملات، وClaude يعمل بأدوات مغلقة، وAntigravity يرفض الصلاحيات. يلزم تطوير عقد المحركات وتوصيل الموافقات والأحداث قبل إعلان دعم الأدوات.

## ما لا ننقله الآن

- cloud computers وVPS وcontainers وphone وvoice وenterprise وربط الحسابات المؤسسية.
- OAuth وmarketplace ومئات custom MCP servers في أول شريحة؛ نبدأ بسيرفر أدوات معروف.
- CDP driver كاملًا أو viewer/noVNC أو تغيير هوية المتصفح وpasskeys. هذه تبعيات إضافية لا يحتاجها السيناريو الأول.
- أوضاع full-access أو bypassPermissions كإعداد تلقائي.
- قاعدة بيانات RuseBot أو store الواجهة؛ نستكمل بنية Loqman الحالية.

## المحركات: ما يستحق الاقتباس

- **Codex:** `server/drivers/codex.ts` يستخدم app-server JSON-RPC، ويستقبل الموافقات كطلبات ويحتفظ بمعرف thread للاستكمال. نأخذ نمط البروتوكول بعد التحقق من نسخة CLI المحلية؛ لا نستبدل adapter الحالي بنسخ الملف الكبير.
- **Claude:** `server/drivers/claude.ts` يقرأ stream events ويربط permission broker وMCP. نأخذ طريقة الربط، مع سياسة صريحة للأدوات والملفات وإعدادات المستخدم.
- **ACP:** `server/drivers/turn-mcp.ts` يجهز MCP servers لـsession/new. تكييف Antigravity الحالي يحتاج دعمًا واختبارات قبل تغيير سياسة الرفض الموجودة.
- **OpenCode:** نراجع adapter المصدر وبروتوكول النسخة المثبتة عند تنفيذ الشريحة؛ لا نوسع صلاحيات agent الحالي لمجرد توصيل browser.

## شكل الاتصال المستهدف

```text
Run Manager → Engine Adapter → Model / CLI
                              ↓ tool call
                    MCP gateway / Tool service
                              ↓
           Tool policy → Approval عند الحاجة → التنفيذ
                              ↓
                 result + run events + artifacts
```

الموافقة تُربط بـrun وبالفعل ومدخلاته ونطاقه. قرار المستخدم لا يتحول إلى تصريح عام لكل الأدوات. كل طلب يُفحص عند التنفيذ، ويُرفض إذا انتهى run أو سُحبت الصلاحية أو تغير مالك التحكم. صلاحيات native tools تحتاج إنفاذًا مستقلًا من المحرك؛ MCP gate وحدها لا تضبط shell المدمج.

## المراحل المقترحة للباك إند

### 1 — المحادثات والموظفون

ربط conversation بملف الموظف وتطبيق تعليماته واختيار engine/model، وحفظ snapshot لإعدادات التشغيل. لا نفتح أدوات جديدة هنا.

القبول: موظفان بإعدادات مختلفة، محادثتان منفصلتان، restart يحفظ التاريخ، والـrun يوضح الإعدادات التي استُخدمت.

### 2 — عقد المحركات والتنفيذ الموحد

نقل المسارات القديمة تدريجيًا إلى Run Manager، وإضافة أحداث نص/أداة/موافقة وعقد capabilities موحد. ترقية adapters على شرائح؛ لا يلزم دعم كل قدرة في كل محرك في نفس الوقت.

القبول: مسار تشغيل محفوظ لكل استدعاء، إلغاء لا يسمح بنجاح متأخر، replay مرتب، وتجربة adapter واحد تبرهن دورة طلب أداة ونتيجتها. استكمال جلسة المحرك يضاف حسب دعمه.

### 3 — سياسة الأدوات وMCP والموافقات

Tool identity وschemas وallow/deny لكل موظف، بوابة stdio MCP لسيرفر معروف، وربط موافقات run بالفعل المنتظر. إدارة subprocess والمهلة وحجم النتائج وتنقية الأسرار.

القبول: أداة ممنوعة لا تُنفذ حتى لو استُدعيت باسمها مباشرة؛ رفض الموافقة أو انتهاؤها أو إلغاء run يمنع الفعل؛ أدوات native خارج MCP تخضع لسياسة المحرك المختبرة.

### 4 — ملفات ومخرجات

أدوات قراءة وبحث وكتابة ضمن workspace، مع preview وhash وموافقة للكتابة وتسجيل artifact. تشغيل shell شريحة اختيارية مستقلة بعد تحديد طريقة الإنفاذ؛ لا نعتمد على cwd فقط لتقييد الأوامر.

القبول: إنشاء ملف مقبول داخل workspace، منع traversal وsymlink، وموافقة منفصلة للاستبدال، وعدم تكرار الأثر عند إعادة الطلب. أخطاء القرص لا تتحول إلى نجاح.

### 5 — متصفح

BrowserService Python؛ نقيّم Playwright Python كتنفيذ أول ونقارن سلوكه المطلوب بعقود RuseBot، قبل تثبيت الاختيار. نبدأ بـopen/read/snapshot/screenshot/click/fill/scroll/tabs/close. نحدد profile ownership ووجهات الشبكة والتنزيل والرفع. eval وتكامل كلمات المرور مؤجلان.

القبول: موقع تجريبي محلي معزول يختبر القراءة والنموذج والتنزيل؛ فصل محادثتين؛ إبطال refs القديمة؛ الإلغاء وtake-control يمنعان أفعالًا متأخرة. يتطلب اختبار الموقع المحلي تصريحًا محددًا في سياسة الشبكة.

### 6 — التحكم بجهاز Windows

تجربة CUA driver المعين أولًا: اكتشافه وإصداره وقائمة أدوات Windows الفعلية، ثم MCP gateway وملكية التحكم وstop وcleanup. Python يملك السياسات والسجل؛ قد يتطلب تشغيل embedded host جزءًا صغيرًا في Electron أو bridge حسب نتيجة التجربة. هذا لا يستلزم تعديل واجهة React.

القبول: اختبار على حساب Windows تجريبي لأداة مراقبة الشاشة ثم نقر وكتابة في برنامج تجريبي، مع إيقاف يمنع أي فعل لاحق وتسليم تحكم واضح وعدم بقاء driver يتيم بعد إغلاق التطبيق.

### 7 — التحقق والتوزيع

اختبارات العقود للمحركات والأدوات، سيناريو متكامل، backup/restore على نسخة آمنة، وحزمة Windows واختبار مستخدم نظيف. دعم engine capability يُعلن وفق اختباراته، لا لمجرد وجود executable.

## الاختبارات التي ننقل فكرتها

## المصدر والتوزيع

المصدر يذكر Apache-2.0 مع استثناء enterprise في `LICENSING.md`، و`NOTICE` يسجل مكونات وتعديلات مشتقة من T3 Code وغيرها. عند نقل كود فعلي أو تكييفه، نحفظ المصدر والإسناد والإشعارات المطلوبة لكل ملف وتبعيته. CUA driver واعتمادياته يحتاجان جردًا منفصلًا قبل التضمين؛ لا نستنتج ترخيصهما من ترخيص RuseBot. نحتفظ باسم وهوية Loqman.

هذه خطة مستندة إلى مراجعة الكود، وليست إثبات تشغيل أو موافقة على توسيع الصلاحيات تلقائيًا.
